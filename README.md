# Voting app, running with Flisk

A five-service voting app (Python `vote`, Node.js `result`, .NET `worker`, Redis, Postgres) that starts with one `flisk up` instead of `docker compose up`. The original `docker-compose.yml` is untouched; Flisk reads the `service.json` files that `flisk import` wrote from it.

## Run it

Needs Node.js 22.12+, Docker (running) and Tilt.

```sh
npx @flisk-sh/flisk up
```

It prints `Flisk is up.` once all services are healthy. Measured on an M-series Mac: about 2 min 10 s from a fresh clone with an empty Docker (no images, build cache or volumes), about 25 s once images are cached.

| What | URL |
|------|-----|
| Vote | http://api.flisk-task-starter.localhost/api/vote |
| Results | http://api.flisk-task-starter.localhost/api/result |
| Tilt UI | http://localhost:10350 |

```sh
npx @flisk-sh/flisk networks              # list the routed URLs
npx @flisk-sh/flisk status                # health of each service
npx @flisk-sh/flisk logs --service worker # follow one service
npx @flisk-sh/flisk up --profile seed     # also run the one-off seed job (3000 votes)
npx @flisk-sh/flisk down                  # stop everything
```

## What is in the repo

- `.flisk/project.json`: the Flisk project.
- `services/flisk-task-starter/<service>/service.json`: one per Compose service (`db`, `redis`, `vote`, `result`, `worker`, `seed`), written by `flisk import .`.
- Generated output (`.flisk/.flisk-out/`, `services/**/.autogenerated/`, root `package.json`, `.tiltignore`) and `.env` are gitignored. `flisk up` regenerates them.

How it was made:

```sh
npx @flisk-sh/flisk import . --dry-run   # preview
npx @flisk-sh/flisk import . --yes       # write project.json + 6 service.json
npx @flisk-sh/flisk up
```

## Changes to the app

Flisk serves both web apps under a path (`/api/vote`, `/api/result`) and strips it before the request reaches the app, so their relative links broke without a trailing slash. Each app now writes a `<base href>` from the `X-Forwarded-Prefix` header Traefik sends:

- `vote/app.py`, `vote/templates/index.html`: `base_href()` passes the prefix to the template.
- `services/flisk-task-starter/db/service.json`: the fixed local database login (`postgres`/`postgres`, as in `docker-compose.yml`) is a `param` instead of a required secret, so a fresh clone starts without a `.env`.
- `result/server.js`: serves `index.html` with the `<base>` tag injected, before the static files. It also now requires `fs` and `path`; the original called `path.resolve` without importing it, a bug hidden because `express.static` answered `/` first.

The prefix is checked against `^(/[A-Za-z0-9._-]+)*$` before it goes into the HTML. Without the header, as under plain `docker compose up`, the base is `/` and both apps behave as before.

I checked it end to end, including `flisk up` from a fresh clone with no `.env`: with and without the trailing slash, both pages load their styles and scripts, a vote posted from the form goes through Redis, the .NET worker picks it up, and the row appears in the `votes` table in Postgres.

## What was hard

All five services were healthy on the first `flisk up` with no edits to the generated files, which I did not expect for three languages and a profile-gated job. The friction was in what came after "Flisk is up" and in trusting what Flisk told me:

- **Voting returned 404 from the URL Flisk prints.** `flisk networks` lists `/api/vote` with no trailing slash. Traefik strips the `/api/vote` prefix, so the page's relative form action (`./`) and stylesheet resolved to `/api/` and `/api/static/...`, which have no route. The results page had the same problem with its scripts, so live counts never loaded. My `curl` check had passed because I posted to `/api/vote/` directly; clicking the button in a browser is what found it. `service.json` cannot add a trailing-slash redirect (its `traefik` block only takes `host`, `pathPrefix` and `healthCheck`), so I fixed it in the apps (see "Changes to the app"). Flisk already generates a `redirectregex` middleware per service; redirecting the bare prefix to `prefix/` there would fix every app served under a path.
- **Edits did not reach the running app.** Compose mounted the source and ran `nodemon`/Flask reload; after import, `vote` runs gunicorn and `result` runs `node`, so saving a file changed nothing until I ran `tilt trigger vote` (about 15 s). "Rebuilds on save" did not hold for these imported services, and nothing in the import output said so.
- **A fresh clone did not start.** The importer turned the Compose `POSTGRES_USER` and `POSTGRES_PASSWORD` into required `secrets` and wrote their values only to `.env`, which it also gitignored. On my machine everything ran; from a clean clone `flisk up` refused with `2 required secrets without a value`, so anyone cloning the repo would need a manual step. They are not secrets (`postgres`/`postgres`, in plain text in `docker-compose.yml` and hard-coded in the .NET worker), so I moved them to `params` in `db/service.json`. A clean clone now starts with one `flisk up`. The importer could keep values that are already committed in the Compose file as `params`, or write a `.env.example` that `flisk up` copies.
- **The dry run under-reports.** `import --dry-run` listed only the dropped `result` entrypoint and port 9229. It said nothing about the `db-data` volume, the `./healthchecks` mounts, the source bind mounts or the `seed` profile. The real import carried all of them over correctly, but from the preview I planned manual fixes for problems that did not exist. A preview should list everything it will write, not only what it skips.
- **The importer writes a value its own validator rejects.** `vote` and `result` got `"port": 80` from Compose, and `flisk up` then warned four times `Invalid port: 80. Must be integer 3000-9999`. The stack ran fine, so the warning is noise, and it makes generated files look wrong on a first run.
- **`build.target: dev` was dropped silently.** Compose builds `vote` from the `dev` stage (Flask with reload); Flisk builds the default `final` stage (gunicorn). It works, but the behaviour changed with no note in the import output.
- **Import is interactive by default.** Without a TTY it asks `(Y/n)`, writes nothing, and exits 0. A coding agent or CI job would read that as success. `--yes` works, but neither the dry run nor its "Next" hints mention it.
- **A plain Compose app gets platform defaults it does not use.** `flisk up` added `DB_PASSWORD` and `JWT_SECRET` to `.env`, planned 16 entities (Infisical, NATS, golden layers) for five services, and printed a "Verdaccio requires a Premium license" line on a free run.
- **The first run builds images this app never uses.** On a cold start Flisk built eight "golden layer" images (`flisk-task-starter-l1` to `-l4-*`, listed sizes adding up to about 2.3 GB) although `.flisk/project.json` has `"golden_image": false` and every service here builds from its own Dockerfile. That is time and disk spent on every first run, and it is why the build cache reached about 6 GB for a five-service app.
- **`flisk doctor` fails on the machine, not the project.** Right after a healthy start it ended with `Doctor failed` and `docker system prune -af` as the first fix, because the disk was low (about 6 GB of images and build cache from this app). The check is real, but a destructive prune as the headline fix on a working stack is alarming.
- **Two backends in one stack share no route.** `doctor` warns that `vote` and `result` lose the shared `/api/flisk-task-starter-management` route. Harmless here, confusing on a first run.

What I would change first: redirect a bare path prefix to `prefix/` in the generated Traefik routes, make `import --dry-run` print the full list of what it writes (volumes, mounts, health checks, profiles, build target, dropped reload), and have the importer emit only values `flisk up` accepts.
