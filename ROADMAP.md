## Vision

Any repository with a `docker-compose.yml` runs on a laptop with one command and works on the first try, whether a person or a coding agent typed it. When a team grows to many projects and many agents in parallel, Flisk is what keeps that affordable on one machine, and that is where Premium earns its price.

The first four rows are free-tier work, ranked for free adoption, which is the priority for these six months. The first row is ranked highest because it is the leak in the funnel: every other row sends people into an import that can still fail silently. In Part 1 of this task I hit five of them in one afternoon, and each would have cost a new user their first impression: a dry run that under-reported, generated ports the validator rejected, required secrets that existed only in my gitignored `.env`, a printed URL whose form posted to a 404, and edits that never reached the running app.

The last row shows how a heavy team reaches Premium without being pushed. I run several Claude Code agents on one repository myself, and it breaks in a predictable order: the second agent collides on ports, the third overwrites the first one's generated files, and by the fourth stack the laptop is out of memory. Add a second and third project and the same thing happens across projects. Making the first two problems free (`flisk worktree`, shared Traefik, the multi-agent `doctor` check) keeps heavy teams on Flisk instead of back on hand-made scripts; the third, stacks that sit idle and eat RAM, is exactly what Sablier idle stop solves, and Premium covers up to 100 project IDs under one key. The early signal I would watch is concurrency, not seat count: a machine that keeps 3 or more stacks up on 5 or more days in two weeks is already paying the memory cost Premium removes, and is one conversation away from a key. The second signal, from the opt-in stats in row three, is a machine with 5 or more Flisk projects started in a month.

## Not now

The provider architecture rewrite (the `make-flisk-unopinionated` epics: provider interfaces for runtime, database, gateway, cache and queue). It is about twenty issues of internal restructuring that a new user never sees, it competes for the same two maintainers as every row above, and it puts the 1.x backward-compatibility promise at risk during the months when adoption matters most. The one slice worth taking now is running an existing Compose project without rewriting it, because it serves the import funnel; the rest can wait until the first-run success rate says the front door is fixed.
